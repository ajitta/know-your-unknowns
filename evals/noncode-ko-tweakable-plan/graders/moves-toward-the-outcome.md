The reply is a plan ordered for the user's review, aiming at the outcome (an
anniversary the parents and siblings are happy with). All of these must hold:
1. It opens with the purpose and done criteria, or marks what is not set (budget, the
   parents' wishes) and asks for it.
2. The decisions most likely to change -- the format the siblings disagree on, the
   budget split, the date -- come first, each with alternatives and what breaks if it
   is wrong.
3. It does not settle the siblings' disagreement for them or assume the parents'
   preferences; it labels those as unknown or asks.
4. Routine steps (booking, invitations) come after the decisions.
Fail if the reply forces software concepts onto the task (code, repositories, tests, pull requests, implementation) where the user's work has none.
