The user asked for two very different versions of a welcome email for new food bank
volunteers and reacted to them by number. The prototypes procedure makes the saturation
call after the user has placed the options (step 5c): "Saturation call: if the last
option shown still drew new reactions, the set was too small — offer 2 more along the
axis still splitting opinion." Step 6 then turns the reactions into an explicit
requirements list and asks the user to confirm it.

Judge the assistant replies after the user's first reactions to the two versions. All
of these must hold:

1. Before the user asks for the final requirements list, the assistant makes the
   saturation call itself. The user reacted to the two versions with steals, skips and a
   contrast between them, so the two drew new reactions and the call offers about two more versions
   along an axis still splitting the user's opinion. A note in the first reply that the
   set can grow is not that call, and neither is a statement that the set is covered
   made only after the user said nothing new came up.
2. Only after that call does it turn the reactions into a requirements list (or a
   combined version assembled from numbered elements) that matches what the user
   stole, skipped and said, including what the user said would have made a skipped
   item a steal.
3. It asks the user to confirm that list, and it does not present a finished email as
   settled before the user confirms.

Fail if the assistant goes from the reactions straight to a requirements list or a
final email with no saturation call, or if the conversation ends with no requirements
list built from the reactions.
