# 인간-AI 협업 프로토콜 대조 — 격차와 개선안

작성: 2026-09-20. 대조 대상: ObsidianVault `30_Resources/인간-AI-협업-프로토콜/` 3편
(01 프로토콜 · 02 Higgsfield 사례 연구 · 03 용어집).
결정 방식: `unknowns:interview` 4문항 1라운드(아래 결정 표).
범위: **이 문서까지.** 스킬 본문 편집은 다음 세션 — 단 G7은 이번에 집행했다.
**집행 상태(2026-09-25, 0.8.0):** G1·G2·G3·G4·G5·G6 모두 스킬 본문에 반영했다. S1(README 재구성)은
하지 않았다. 항목별 실제 편집 내용과 계획과 달라진 점은 맨 아래 "집행 기록" 절에 있다.

## 왜 대조했나

프로토콜은 "의도 정렬형·명세 및 평가 주도 인간-AI 협업 프로토콜"을 네 층으로 정리한다:
인식적 상태 공개 → 요구사항 도출·용어 정렬 → 의도·목표·완료 조건 명세 → 승인형 실행과
현실 검증. 이 플러그인과 대상 문제가 같으므로, 프로토콜을 사각지대 점검표로 썼다.

## 두 체계의 축이 다른 지점

플러그인의 축은 **지도–영토 격차**이고 최적화 대상은 *사용자의 인식 상태*다. 뒷단이 그
증거다 — `quiz`는 "당신이 설명할 수 있는가", `buy-in`은 "리뷰어를 설득할 수 있는가"를 묻는다.

프로토콜의 축은 **의도 정렬 + 명세·평가 주도**이고 최적화 대상은 *결과물의 타당성*이다.
뒷단이 "주장 유형별 검증 → 실제 환경에서 최초 목적 달성 확인"이다.

앞단(요구사항 도출, 용어 정렬, 사각지대, 승인 관문)은 거의 겹친다. 오히려 플러그인이 더
정교하다 — 프로토콜이 한계로 적은 "승인 지점이 많으면 속도가 떨어진다"를 `loop`의 tier
축소, `plan`의 size gate, 훅의 threshold가 이미 완화한다. **격차는 전부 뒷단에 있다.**

## 결정 표

| 반경 | 질문 | 결정 | 근거 |
|---|---|---|---|
| architecture | 뒷단을 프로토콜 쪽으로 확장할까, 현재 축을 유지할까 | **축 확장** | "이해했는가"에 "타당한가"를 더한다. G4·G5가 살아난다 |
| data | 완료 조건(G1)을 어디에 둘까 | **`plan`의 필수 선행 섹션** | 12번째 스킬을 만들지 않고, reviewer 패킷의 빈칸을 메운다 |
| compatibility | 근거·확신도 라벨(G2) 적용 범위 | **사실 주장이 많은 곳만** — `blindspot`, `unknowns-scout`, `reference`, `teach-me` | 전면 적용은 모든 산출 스키마와 아티팩트 조립 로직을 건드린다 |
| cost | 이번 세션 범위 | **개선안 문서까지** + G7 즉시 집행 | 되돌리기 비용이 가장 싼 지점 |

미결: G3·G6의 배치는 자명한 자리가 하나씩이라 질문하지 않았다(아래 각 항목에 기재).
이견이 있으면 그 두 항목만 다시 고르면 된다.

## G1 — 완료 조건이 `loop` 안에만 있다

**근거(검증됨).** `skills`·`agents`·`hooks`·양쪽 README 전체에서 `done criteria` /
`success criteria` / `acceptance`를 검색한 결과는 `skills/loop/SKILL.md` 27·28·30·62행뿐이다. README가 권장하는 직접 호출 경로
(`/unknowns:plan`, `/unknowns:interview`)로 들어오면 인수 조건이 한 번도 고정되지 않는다.
더 문제인 건 62행 — `independent-reviewer`에게 넘길 패킷의 첫 항목이 "done criteria
(step 1)"인데, `loop`를 돌리지 않으면 **존재하지 않는 입력을 요구한다.**

**결정.** `plan`의 필수 선행 섹션.

**편집 대상.**
- `skills/plan/SKILL.md` — Procedure 1과 2 사이에 새 단계. 문서 맨 앞에 고정 섹션
  "목적 / 인수 조건 / 절대 깨지면 안 되는 기존 동작 / 허용 비용·변경 범위" 4칸.
  비어 있으면 한 라운드 `AskUserQuestion`으로 받고, 사용자가 건너뛰면 "인수 조건 미정 —
  reviewer가 적합성 판정을 할 수 없음"을 문서에 명기한다(조용히 넘어가지 않는다).
- `skills/loop/SKILL.md` step 6 — step 1에서 이미 고정했으면 재질문하지 않고 인용한다는
  한 줄. 중복 질문이 loop 사용자에게 가장 먼저 거슬리는 지점이다.
- `agents/independent-reviewer.md` — 패킷에 인수 조건이 없을 때의 행동 규정: 추측하지 말고
  "적합성 판정 불가"로 보고한다.

**검증.** `grep -rn 'done criteria' skills agents`가 `plan`에서도 잡힌다.
`/unknowns:plan`을 loop 없이 실행했을 때 4칸이 먼저 나온다.

**위험.** `plan`의 size gate(≤2파일)를 통과하는 작은 작업에서 4칸이 과하다 → size gate를
통과한 경우 인수 조건은 한 줄로 축약한다는 예외를 같이 적는다.

## G2 — 모델 주장에 근거·확신도 칸이 없다

**근거(검증됨).** 스킬 11개와 에이전트 2개 전체(`references/` 포함)에서
`confidence`/`calibration`/`uncertain` 검색 결과는 1건뿐이고, 그나마 `loop` step 5의 기술
가정이라 주장 확신도가 아니다. `blindspot`과 `unknowns-scout`의 발견 표는
`종류 / 발견 / 왜 문제인가 / 권장 조치` 4칸이고 근거 칸이 없다.
증거 앵커(`file:line`)를 강제하는 곳은 세 군데 — `quiz`("Where: file:line"),
`buy-in`(근거 없으면 limitations로 내린다), `independent-reviewer`(출력 항목마다 file:line) —
인데 **셋 다 뒷단이다.** 앞단에서 만들어진 주장이 뒷단에 가서야 근거를 요구받는다.

프로토콜 1층의 AI 쪽 요구 — 불확실성 추정, 기권, 출처·가정·검증 한계 명시 — 는 산문 규칙으로는
세 군데 있다: `unknowns-scout`("Never invent findings. If investigation scope was
insufficient, state where to look further"), `buy-in`("근거 없으면 limitations로 내린다"),
`quiz` 1부 4항("모델이 보증할 수 없어 사용자가 직접 확인해야 하는 것").
**문제는 규칙의 부재가 아니라 규칙을 담을 칸의 부재다.** 셋 다 산출물 서식에 대응하는 칸이 없어
지켰는지 안 지켰는지가 결과물에서 드러나지 않는다 — 발견 표의 4칸은 전부 채워져 있고,
추정으로 쓴 행과 읽고 확인한 행이 같은 모양으로 나란히 선다.

**결정.** 사실 주장 비중이 높은 네 곳만: `blindspot`, `unknowns-scout`, `reference`, `teach-me`.

**편집 대상.**
- `skills/blindspot/SKILL.md` 3·4단계와 `agents/unknowns-scout.md` 출력 표 — 칸 두 개 추가.
  **근거**(`file:line` / 커밋 해시 / 문서 URL)와 **확인 상태**(확인됨 / 추정 / 미확인).
  "확인됨"은 실제로 읽은 것에만 쓴다.
- 같은 두 파일 — **미확인 항목은 발견 표에 넣지 않고** "확인 필요" 섹션으로 내린다.
  발견 표의 건수 집계("landmine 4건")가 추정으로 부풀지 않게 하는 장치다.
- `skills/reference/SKILL.md` 3단계 semantics map — 각 행에 레퍼런스 원문의 위치를 단다.
- `skills/teach-me/SKILL.md` 4단계 어휘 사다리 — 용어마다 출처 한 개. 프로토콜의 경고
  "도메인 용어는 잘못된 전제를 정교하게 만들 수도 있다"가 정확히 이 스킬을 가리킨다.

**검증.** `evals/`에 케이스 추가 — 근거 없는 발견이 표에 올라오면 실패.

**위험.** 근거 칸이 형식적으로 채워진다(파일명만 적고 행 번호 없음 등). 완화: 확인 상태를
3값으로 두고 "추정"을 정당한 선택지로 만든다. 2값(있음/없음)이면 전부 "있음"이 된다.

## G3 — 사용자의 known knowns를 묻지 않는다

**근거.** 이름이 know-your-unknowns인데 사분면의 네 번째 칸을 쓰지 않는다. `prototypes`가
unknown knowns, `blindspot`이 unknown unknowns, `interview`가 known unknowns를 맡는데
**사용자가 이미 아는 것을 선언하는 지점이 없다.** 정확도만의 문제가 아니라 비용 문제다 —
사용자가 이미 확신하는 영역을 scout이 다시 판다.

프로토콜 1층은 아는 것 / 모르는 것 / 확인되지 않은 가정 / 직접 판단 가능한 것 /
판단 기준 자체를 모르는 것의 구분에서 시작한다.

**결정(질문 없이 배치).** `blindspot`과 `interview`의 1단계에 한 라운드.

**편집 대상.** 두 SKILL.md의 Procedure 1 — 조사 전에 세 칸을 받는다:
① 이미 확실한 것(조사 범위에서 제외) ② 가정인 것(**우선 검증 대상**) ③ 판단 기준 자체를
모르는 것(→ `teach-me` 연결). ②가 핵심이다 — 선언된 가정은 배제가 아니라 최우선 표적이 된다.
사용자가 건너뛰면 전체 조사로 진행한다(강제하지 않는다).

**검증.** 선언된 ①영역이 scout 패킷의 제외 목록에 실린다.

**위험.** 사용자가 틀리게 확신한 것이 조사에서 빠진다 — 이게 프로토콜이 경고한 바로 그
실패다. 그래서 ①은 "제외"로, ②는 "우선 검증"으로 비대칭 처리하고, ①에 대해서도
"확신 근거가 최근 것인가"를 한 줄 되묻는다.

## G4 — 검증이 테스트 모양 하나다

**근거.** `independent-reviewer`의 4개 항목(계획 부합, 이탈 로그 판정, 테스트 통과-현실 실패,
확인 완료 목록)은 모두 **코드·실행·로그로 확인되는 것**을 대상으로 한다. 사실 주장의 원출처
대조도, 추론의 전제·반례 검사도 항목에 없다. `blindspot`의 "이 모듈은
마이그레이션 중", `teach-me`의 도메인 용어, `reference`의 동작 해석은 전부 **사실 주장**인데
출처 대조 절차가 없다.

프로토콜의 표가 정확히 이 구분을 요구한다: 기능은 테스트, 사실은 원출처 대조, 추론은
전제·반례 검사, 전체 결과물은 현실 환경 타당화.

**결정.** 축 확장 결정에 따라 포함.

**편집 대상.**
- `agents/independent-reviewer.md` — 5번째 검증 항목 "주장 유형별 검증": 리뷰 대상에 사실
  주장이 있으면 원출처 대조, 추론이 있으면 전제와 반례 검사. 주장 유형을 못 가르면 그렇게
  적는다.
- `skills/loop/SKILL.md` step 8 — reviewer에게 넘기는 패킷에 "이 작업에서 사실 주장에
  해당하는 항목" 목록을 추가한다.

**검증.** 사실 주장이 섞인 diff로 reviewer를 돌렸을 때 출처 대조 항목이 보고서에 나온다.

## G5 — 효과성 확인 시점이 없다

**근거.** `loop` step 10 가치 리뷰는 작업 종료 **직후**다. 프로토콜은 실제 환경 타당화와
지속 평가를 요구하는데, 플러그인에는 "나중에 다시 본다"는 장치가 없다. 스코어카드도
"몰랐던 것 발견? / 결정 변경?" 두 칸으로 *플러그인의* 가치를 재지, *작업 결과물의* 현실
효과를 재지 않는다.

**결정.** 축 확장 결정에 따라 포함.

**편집 대상.**
- `skills/loop/references/scorecard.md` 파일 형식 — 열 두 개 추가: **재확인일**과
  **현실 확인 결과**. 재확인일은 작업 종료 시 사용자가 정한다(기본값 없음 — 작업마다 다르다).
- `skills/loop/SKILL.md` step 10 — 가치 리뷰가 "무엇을 보면 효과를 확인할 수 있는가"와
  "언제 볼 것인가"를 함께 받는다.

**근거가 되는 자기 사례.** `docs/value-contract.md`가 이미 이 기법을 쓴다 — "다음 확인에서
넘기면"을 날짜로 못 박는 것. 그 문서의 표현 그대로: *"확인을 안 하면 영원히 발동하지 않는다."*
같은 기법을 산출물에도 적용하는 것이다.

**위험.** 재확인일이 아무도 안 보는 열이 된다. 이건 실제로 일어났다 — G7 참조. 완화책은
이 항목의 범위를 넘으므로(알림 기제 필요) 열 추가까지만 하고 미결로 둔다.

## G6 — 계획이 append-only로 표류한다

**근거.** `notes`는 이탈을 **기록**하지만 `plan` 문서는 갱신되지 않는다. 이탈이 쌓이면
승인받은 계획과 실제 작업이 벌어지는데, 문서 어디에도 "그래서 계획의 3번 항목은 이제
무효"라고 적히지 않는다. 프로토콜의 change control은 명세 자체의 개정과 **재승인**을 요구한다.

**결정(질문 없이 배치).** `notes`에 규칙 한 줄.

**편집 대상.** `skills/notes/SKILL.md` — 이탈이 `plan`의 **결정 항목**(스키마/인터페이스/
UX 계약)을 무효화하면, 로그만 남기지 말고 해당 항목을 개정하고 재승인을 받는다.
기계적 항목의 이탈은 로그로 충분하다. 이미 있는 에스컬레이션 규칙(아키텍처·사용자 가시
동작·데이터·보안은 멈추고 묻는다)의 문서 쪽 짝이다.

**검증.** 결정 항목을 무효화하는 이탈을 만들었을 때 plan 문서가 갱신된다.

## G7 — 가치 계약이 발동했는데 미집행이었다 (이번에 집행함)

**근거(검증됨).** `docs/value-contract.md`가 못 박은 발동일은 2026-09-09 — "60일간 신규
스코어카드 행 0건이면 README에 미측정(unmeasured) 표기". `docs/value-scorecard.md`의
마지막 행은 2026-07-11 1건이고, 오늘 기준 71일이 지났다. 두 README 모두 해당 표기가 없었다.

개선안이 아니라 밀린 숙제다. 프로토콜의 "한 번의 완료 판정으로 끝나지 않는다. 환경과 모델이
바뀌면 지속 평가가 필요하다"가 이 항목을 가리킨다.

## S1 — 구조: 스킬 목록을 네 층으로 다시 묶는다 (선택)

README의 `Skills at a glance`는 Phase 열이 Before / During / After다. 프로토콜의 네 층
(인식 → 정렬 → 명세 → 실행·검증)으로 묶으면 **명세 칸이 `plan` 하나뿐이라는 사실이 표에서
바로 보인다.** G1을 반영하면 그 칸이 채워지는 것도 같이 보인다.

문서 변경이지만 지향점 변경이기도 하다. 축 확장 결정과 함께 가면 자연스럽고, 따로 하면
의미가 약하다. G1·G4·G5가 실제로 반영된 뒤에 하는 것이 순서상 맞다.

## 이 개선안의 가장 약한 부분

**G5의 재확인 열.** 근거가 가장 얇다. 열을 추가해도 그 날짜를 누가 보는지에 대한 답이 없고,
같은 실패(G7)가 이 저장소 자신에게서 이미 한 번 일어났다. 알림 기제 — 훅이든 스코어카드를
읽는 세션 시작 점검이든 — 없이 열만 추가하면 지켜지지 않는 약속을 하나 더 만드는 것이다.
다음 세션에서 이 항목을 착수하기 전에 "누가 언제 이 열을 읽는가"를 먼저 정할 것.

두 번째로 약한 것은 **G2의 확인 상태 칸**이 형식적으로 채워질 위험이고, 완화책(3값 척도)은
검증되지 않은 설계 추측이다.
